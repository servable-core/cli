# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

For fast copy-paste usage, see `QUICKREF.md`.

## What this repo is

`@servable/cli` (`bin: servable`) — the Servable command-line tool: `app`, `auth`, `protocol`, `model` command groups, plus (from unischema) `schema build|plan|apply|contract`. Commands live under `src/commands/<group>/`, one file per subcommand, auto-discovered by `@clinext/sdk`'s `launch()` (`src/app.js`) — a group's `index.js` registers the group itself (`_clinextType: 'command'`, `position`), sibling files in the same directory become its subcommands.

## Commands (developing this CLI)

- Install: `yarn install`
- Run locally: `node src/app.js <command>` (or link the package and run `servable <command>`)

The old `src/commands/app/schema.js` was **deleted** — despite its description ("Generate schema documentation"), its handler actually scaffolded a new protocol via `ChunkProtocolContent`, unrelated to schema entirely. ### `src/lib/schema/loadServableConfig.js` — read this before touching any schema command

Every schema command starts here: loads the app's `servable.config.js` from `process.cwd()`, fills in the two defaults `@servable/tools`' `buildSchema()` needs (`rootProtocolPayload`, `protocols.local`), and sets a **minimal** `global.Servable` stub — just `{ App: { Object, User, Role } }`, three bare classes with no behavior.

**This is deliberately not a real engine bootstrap, and that was a real design mistake corrected once already.** An earlier version of this file imported `@servable/parse-server-engine` and ran `engine.createApp()`/`engine.adaptApp()` to get the *real* Parse-bound classes, on the theory that `buildSchema()`'s output might silently differ without them (some protocol `class.js` files import-crash without a real `Servable.App.Object`, caught elsewhere and merely logged — so an incomplete stub was a real hypothesis, not a hunch). Tested directly rather than assumed: `classes` (fields/indexes/classLevelPermissions — everything Parse actually receives) came back **byte-identical** between the minimal stub and a fully-hydrated real engine, across this codebase's whole protocol tree. The one place the real engine's output *did* differ (`Servable.engine.formatAppClassesSchemas` injecting four framework-default classes) turned out to be a bug in `@servable/tools` itself — `buildSchema()` was calling an engine-specific method unconditionally — and was fixed at the source (see `@servable/tools`'s own `CLAUDE.md`), not by forcing this package to carry a specific engine as a dependency.

**If you're tempted to add `@servable/server` or any `@servable/*-engine` package as a dependency of this CLI to "make schema building more correct," don't, without first proving — the same way, empirically, not by inspection — that the minimal stub actually produces different `classes` output.** It didn't, once, for a plausible-sounding reason that turned out to be somewhere else entirely. A CLI that computes schema diffs has no principled reason to depend on which engine an app happens to use.

**One thing the stub DOES need to replicate, found later and genuinely deploy-blocking**: `@servable/server`'s own `adaptConfig/basic.js` unconditionally prepends its bundled `protocols/` directory (`uniquerefable`, `servableconfigurable`, `servableautoseedable`, `manualable`, the disposable*able triggers) to `servableConfig.protocols.local` on every real boot. Without the same prepend here, this CLI never resolved those protocols at all — confirmed empirically against backend/main: the real, `adaptConfig`-hydrated build produced 72 classes (hash `88fefe627640`) against 63 (hash `1ee54142594d`) from the un-prepended stub, 50 real, purely-additive schema elements missing. Since the boot-time drift check hashes a real boot's own `buildSchema()` output, the previously-committed artifact would have hash-mismatched and refused to boot the moment this was deployed. Fixed in `loadServableConfig.js` by resolving `@servable/server`'s installed path via `require.resolve('@servable/server/package.json')` (anchored at the app's own directory, matching how the app's own runtime would resolve it) and prepending its `src/protocols` — this reads a filesystem fact about a dependency the app already has installed, it does not import or hydrate `@servable/server`, so it isn't the same mistake as above. See `.docs/technical/unischema-plan.md`'s "Migrating `@servable/server`'s own bundled protocols" section for the full empirical trail, including re-verifying with the real `adaptConfig` function directly (not a re-implementation) after the fix.

### The four commands

- **`build`** — `compileArtifact()` → writes `servable.schema.json` next to `servable.config.js`. Carries forward `compatibilityFloor`/`breakingChanges` from whatever was already committed (they're persistent state, not derived schema content, and aren't part of the hash) — a plain rebuild never resets them.
- **`plan [--ci]`** — diffs committed `servable.schema.json` against a fresh build. No database involved. `--ci` exits 1 on any breaking change (used in `.husky/pre-push` and `scripts/docker/{staging,production}/build.sh` in consuming apps — see `backend/main`'s own `CLAUDE.md`).
- **`apply`** — `build` + refuses if `plan` shows *any* breaking change (deprecated or not). Additive-only, unconditionally.
- **`contract --reason=... [--force]`** — the only command allowed to remove anything. Refuses a removal unless the field/class was already marked `"deprecated": true` on the *previous* committed artifact (not the fresh one — the point is prior warning, not simultaneous removal) — `--force` bypasses that for a field known to be safe regardless (e.g. added and removed in the same release). Bumps `compatibilityFloor` in `servable.schema.json`; never touches a database (see below).

### No database, anywhere in this command group

`apply`/`contract` write only to `servable.schema.json`. The `compatibilityFloor` bump `contract` makes is picked up by the running server's own boot-time check (`@servable/server`'s `checkSchemaCompatibility`), which is what actually persists it to `ServableSchemaState` — not this CLI. This mirrors the `@servable/server` decision above: don't reach for a dependency (here, `mongodb`) to reuse a capability the thing that actually needs it (the server, at boot) already has to have anyway.

### Other unischema-related fixes, found by tracing actual call paths rather than assuming

- **`_importJSONDefault` (in `@servable/tools`, consumed by every schema read here) used to swallow a malformed `schema.json` to `null`**, indistinguishable from "no schema.json at all" — a broken file silently produced a build missing that protocol's classes, not a build failure. Now rethrows with the file path. See `@servable/tools`'s own `CLAUDE.md`.
- **`servable protocol new`/`servable app new` scaffolded the deleted `schema/1.0.0/index.json` convention.** Fixed both chunk templates (`lib/chunks/{protocol,app}/content/template/`) to emit flat `schema.json` — every protocol/app created going forward now starts with a schema the loader actually reads.
- **`servable model add` never registered the new class in the target protocol's `schema.json` at all**, and the class-name-uniqueness check in its own prompt always saw an empty list. Root cause: `protocolSchemaRaw.js` (two identical copies, `lib/newlib/classInformations/` and `lib/prompts/classInformations/`) still read the deleted `schema/<version>/index.json` path — fixed both to read `schema.json` directly. Separately, the actual write-back (`updateProtocolClasses`, merging the new class into `schema.managed.classes`) lived in `model/content/write.withprotocol.js`, a variant nothing imported — `model/content/index.js` was wired to plain `write.js` instead, so the class-registration step was silently orphaned (same "dead file next to the live one" pattern as `generateSchema`, see above). Folded the write-back into the live `write.js`, unconditionally (there's no "version" left to gate it behind), and deleted `write.withprotocol.js` plus two unrelated dead scratch files (`write copy.js`, `write copy 2.js`) that sat next to it.
- **`servable app new`'s engine picker (`engineId`, backed by a real registry lookup) was decorative.** The generated `index.js` hardcoded `import engine from "@servable/parse-server-engine"` regardless of what was picked, and the generated `package.json` never listed any concrete engine as a dependency at all. Templated both with `<%= engineId %>` (this chunk's `copy` already renders every file through EJS with `payload` — including `engineId` — as the render context, same mechanism `docker-compose.yaml`'s templating uses elsewhere in this codebase) — verified by rendering both templates directly with two different `engineId` values. Found while checking whether `@servable/cli`'s scaffold templates mentioning Parse Server were architecture violations (mostly not — see the separate note above on why a scaffold defaulting to the one real engine is fine) or actual bugs (this one was). A deeper, related finding — `@servable/server` itself passes the concrete engine's raw `server` object straight into every protocol's `beforeInit`/`afterInit` hooks, unabstracted — was filed as PEAKUB-230 rather than fixed here; it needs a deliberate design pass, not a quick patch.
- **Full sweep of literal "Parse Server" wording in every `lib/chunks/*/template/` file** (what actually gets copied into a generated app/protocol — CLI-internal comments/code outside `template/` were left as-is, they're not distributed). Two different fixes depending on whether the surrounding scaffold has an `engineId` in scope at render time: `app/content/template/package.json`'s `keywords` (app-scoped, `engineId` is available) now reads `["servable", "<%= engineId %>"]` instead of hardcoding `parse`/`parse-server`. Everything under `protocol/content/template/` and `triggers/template/` (JSDoc on `afterinit`/`beforeinit`/`functions`/each trigger's `request` param, plus `app/models/_user/triggers/afterfind.js`'s prose) is protocol-scoped — `protocol new` never asks for an `engineId`, so these were genericized to "the engine's server instance" / "the engine's cloud function request object" rather than computed, since naming a specific engine there would be asserting something the scaffold doesn't actually know. `protocol/shell/template/package.json`'s `keywords` dropped `parse-server` for the same reason. `releaseType/template/.github/workflows/release.yml`'s top comment (a Parse Server GitHub Actions link used only as scaffolding inspiration, no functional role in a generated repo's own CI) was removed outright rather than genericized — it had no payoff for keeping.
- **`commands/model/test.js` crashed the entire CLI, every command, including bare `servable` with no arguments.** It imported `../../lib/chunks/class/content/index.js`, a directory that has never existed. `app.js` discovers commands by directory-scanning `src/commands/` and importing them eagerly, not lazily — so this one broken file's import failure took down the whole binary, not just `model test`. This had been masked all session because every schema command was tested by importing its own file directly (`import('.../commands/schema/plan.js')`), which never exercises `app.js`'s command-tree loading at all. Only surfaced once `@servable/cli@unischema` was actually installed as a real dependency and run via `node_modules/.bin/servable` for the first time. Confirmed via an import-check sweep of every file under `src/commands/` that this was the *only* broken one. Deleted it — nothing referenced it (`commands/model/index.js` doesn't wire it, no doc mentions a `model test` command), dead scaffolding, not a real feature loss.

**Lesson for testing this package specifically**: importing a command file directly is fine for testing that command's own logic, but it does not prove the CLI as a whole is runnable — only actually invoking `node_modules/.bin/servable` (or `app.js`) exercises the eager command-discovery path that a real user hits on every invocation.
